# 案例库低成本质量门禁工作流

## 目标与边界

本流程服务于纯静态 React 案例库，目标是在不降低案例真实性、来源可追溯性、五层分析与可下载 PDF 质量的条件下，减少重复检索、重复图像检查、重复构建和无效上传。每批固定为 **5 案**；仅当 5 案同时通过准入门槛，才启动一次性生产。

> 不可削减的底线是：整体展陈／制作或明确馆方策展责任、当前运营、清晰叙事、两张人工审核的真实已建成室内图、原始来源、五层分析、每案独立 PDF、ID 唯一及关键详情页可用性。

| 阶段 | 最小执行动作 | 只做一次的证据 | 不再执行的低效动作 |
|---|---|---|---|
| 候选发现 | 优先设计方项目页；仅在缺运营或叙事时补一个馆方页 | 设计责任、现行开放、叙事、两张图的来源与审核结论写入同一台账 | 对同一候选跨多轮泛搜；未达门槛前下载、写PDF或改前端 |
| 5案闭池 | 运行单个确定性台账门禁 | 精确5案、字段完整、与全库ID／标题排重 | 逐案发布、逐案全量构建、边搜边上传 |
| 媒体 | 批量下载10图、单脚本规范化、一次批量上传 | 冻结下载清单、最终媒体清单、上传路径清单 | 同一图多次下载／上传；生成无关联系表或重复逐图审阅 |
| 内容与PDF | 复用固定五层结构与报告主题；一次生成5份 | 每案内容JSON、Typst源、构建计划、验证JSON | 逐段编译；为无新增信息的版式反复重写 |
| 前端与测试 | 一次性接入5个CaseItem；新增一份批次测试 | 尾部顺序、资源路径、五层字段与ID门禁 | 每加一案反复运行全库测试或截图所有历史页面 |
| 发布 | 批末仅运行一次完整门禁并保存一个检查点 | `pnpm test`、ID检查、类型、构建与代表性浏览器回归 | 中间检查点、重复发布、已通过构建后的无差异重跑 |

## 具体执行规则

候选阶段采用“**设计方优先、馆方补强**”的双来源上限：设计方项目页负责整体展陈责任及原始现场图，馆方页面仅用于确认当前开放和叙事。若这两页不能闭合证据，立即标为暂缓；不以第三方报道、效果图或旅游照片继续消耗检索资源。

图像阶段只做三次有效检查：在候选台账中人工确认原始图真实性与章节差异；规范化脚本以 Pillow 检查文件可打开与尺寸；在最终媒体中抽检每案一对图的可读性与差异。图片只保留外置原件并只上传一次，网页和 PDF 统一使用同一份持久化路径清单。

内容与 PDF 阶段使用固定的“平面与动线、策展叙事、展项设计、布展与图文、研究判断”五层结构。事实仅来自台账中的来源，研究判断以条件性语言表达。每案 PDF 只在内容依赖闭合后编译一次；失败时按诊断统一修复后再做一次重编译，避免逐标题试错。

前端阶段只新增一个批次数据模块、一份批次测试和必要的历史尾部偏移更新。测试分为轻量局部门禁与批末全量门禁：开发中仅运行新批次测试及ID检查；准备发布时按固定顺序运行 `pnpm test`、`pnpm run verify:case-ids`、`pnpm run check`、`pnpm run build`。浏览器仅核验最新首卡、一个桌面详情、一个移动详情、图片／PDF入口、相邻导航以及受影响地区筛选。

## 第三十五批恢复原则

当前沙箱恢复到第三十四批已发布基线，任何未保存的第三十五批候选、下载和上传状态均不视为可用成果。后续按本工作流从台账开始重新建立该批，不复用未被持久化进项目或外置资产目录的临时结果；在新台账精确闭合5案前，不触发媒体、PDF、前端或发布操作。
